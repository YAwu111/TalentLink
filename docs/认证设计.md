# 认证与权限设计

> 对应模块：`backend/app/core/security.py`、`app/services/auth_service.py`、`app/api/routes/auth.py`、
> `frontend/src/api/http.ts`、`frontend/src/stores/auth.ts`

## 1. 双令牌方案

| | 访问令牌 Access | 刷新令牌 Refresh |
|---|---|---|
| 形态 | JWT（HS256） | 48 字节随机串，明文只下发一次 |
| 有效期 | **1 分钟**（`ACCESS_TOKEN_EXPIRE_MINUTES`） | 7 天 |
| 存放 | httpOnly Cookie，`Path=/api` | httpOnly Cookie，`Path=/api/auth` |
| 服务端状态 | 无（无状态） | `refresh_tokens` 表存 SHA-256 |
| 撤销 | 靠短过期 | 立即吊销 |

两者都走 httpOnly Cookie，前端 JS 读不到令牌值，从根上避免 localStorage 被 XSS 读取。
刷新令牌的路径限定为 `/api/auth`，普通业务请求不会携带它。

## 2. 为什么刷新令牌不用 JWT

JWT 自包含且不可撤回：用户点「退出登录」后，只要刷新令牌没过期就仍能换出新访问令牌，
管理员封禁账号也无法立即生效。因此刷新令牌使用不透明随机串，数据库只保存其哈希：

- 支持吊销（`revoked_at`）
- 支持轮换（`replaced_by` 记录后继令牌）
- 数据库泄露也无法反推出可用令牌

## 3. 访问令牌载荷

```json
{
  "sub": "2",
  "role": "employer",
  "type": "access",
  "jti": "a71caec0d6056413",
  "iat": 1793759596,
  "exp": 1793759656,
  "iss": "talentlink",
  "aud": "talentlink-web"
}
```

三个必须校验的点：

| 校验项 | 目的 |
|---|---|
| 签名（HMAC-SHA256 + secret） | 防篡改 |
| `exp` / `iss` / `aud` | 防过期与跨系统重放 |
| `type == "access"` | **防止刷新令牌被当作访问令牌使用** |

此外每次请求仍会按 `sub` 查一次用户，确认 `status == active`——JWT 无状态，
不查库就无法做到「封禁立即生效」。

## 4. 登录 / 刷新流程

```
登录：校验密码 → 查账号状态 → 签发 access(1min) + refresh(7d) → 两个 Cookie
刷新：读取 refresh Cookie
      ├─ 查不到哈希        → 401
      ├─ 已吊销（被重用）  → 吊销该用户全部会话 → 401   ← 盗用检测
      ├─ 已过期            → 401
      └─ 正常 → 作废旧令牌 → 签发新的一对令牌
```

**重用检测**是这套设计的核心防线：刷新令牌每次使用后立即作废并生成新的，
若某个旧令牌再次出现，说明它被复制过，系统直接吊销该用户所有会话。

## 5. 前端 401 处理：单飞（single-flight）

访问令牌只有 1 分钟，页面并发请求很容易同时收到 401。若各自发起刷新，
第二个之后的请求会用到已作废的旧令牌，直接触发服务端的重用检测，把用户踢下线。

因此 `src/api/http.ts` 用一个共享 Promise 收敛刷新请求：

```ts
let refreshPromise: Promise<AuthResult | null> | null = null
```

第一个 401 发起刷新，其余请求挂起等待同一个结果，成功后统一重放原请求。

同时 `auth` store 在拿到 `expires_in` 后，提前 15 秒静默续期，绝大多数情况不会走到 401 分支。

## 6. 权限控制

```python
# 路由级
@router.get("/admin/xxx", dependencies=[Depends(require_roles(Role.admin))])
```

- `get_current_user`：解析 Cookie → 验签 → 查库 → 校验状态
- `require_roles(*roles)`：角色守卫工厂，越权返回 403
- 前端 `router.beforeEach` 按 `meta.requiresAuth` / `meta.guestOnly` 做导航守卫，
  **前端守卫只负责体验，真正的权限判定在后端**

## 7. 安全措施清单

| 措施 | 说明 |
|---|---|
| 密码哈希 | bcrypt（自带盐，cost 默认 12） |
| 统一错误文案 | 登录失败统一返回「用户名或密码错误」，不暴露用户名是否存在 |
| 注册角色限制 | 注册接口只接受 `seeker` / `employer`，管理员账号只能由种子数据创建 |
| Cookie 属性 | `HttpOnly` + `SameSite=Lax`；生产环境置 `COOKIE_SECURE=true` 强制 HTTPS |
| 令牌类型隔离 | `type` 声明 + 校验，访问令牌与刷新令牌不可混用 |
| 会话可撤销 | 登出即吊销刷新令牌；检测到重用则吊销全部会话 |
