# 企业资料与文档识别设计

> 当前阶段：企业资料手动完善 + 上传页 + B1/B2 文档与认证 + B3 管理员审核 + P4 本地 OCR/规则识别 + 前端 HTTP provider + B4 企业认证状态展示。LLM 增强、真实 OCR 云服务与岗位/投递硬阻断尚未接入。

## 1. 路由与布局

登录后统一使用 `AppLayout`：

- 工作台 `/`
- 企业资料 `/employer/profile`
- 资料上传 `/employer/profile/upload`

企业账号的顶栏显示三个 tab；其他角色当前只显示工作台。tab 激活下划线由 Motion `layoutId` 实现共享过渡。

## 2. 企业资料字段

沿用现有 `companies` 表，不新增字段：

| 字段 | 权重 | 说明 |
|---|---:|---|
| name | 30 | 企业名称 |
| industry | 15 | 经营行业 |
| phone | 20 | 企业电话 |
| address | 15 | 企业地址 |
| intro | 20 | 企业简介 |

完整度 = 已填写字段的权重和。`verified`（身份认证）独立于完整度，不参与计算。

`is_complete` 要求 5 个字段全部非空。字段可以暂时为空并保存草稿，但此时：

- `can_receive_applications = false`
- 企业端显示“资料尚未完整”提示
- 后续岗位发布、投递、推送接口统一调用 `ensure_company_complete` 做硬阻断

> 当前还没有岗位与投递接口，因此本阶段只实现状态与可复用校验函数，硬阻断在对应模块接入时生效。

## 3. 后端接口

### GET `/api/employer/company`

仅 `employer` 角色，返回自己的企业档案：

```json
{
  "id": 1,
  "name": "星河科技有限公司",
  "industry": "互联网/软件",
  "phone": "021-58889000",
  "address": "上海市浦东新区张江路 88 号",
  "intro": "专注企业级 SaaS 产品研发……",
  "verified": true,
  "completeness": 100,
  "is_complete": true,
  "missing_fields": [],
  "can_receive_applications": true,
  "updated_at": "2026-11-04T10:31:44"
}
```

### PATCH `/api/employer/company`

字段级自动保存，payload 只带发生变化的字段：

```json
{ "phone": "021-58888888" }
```

允许空字符串草稿；长度上限：name 100、industry 50、phone 20、address 200、intro 2000。

服务层在每次保存后重新计算完整度，并返回 `updated_at` 供前端显示“已保存时间”。

## 4. 自动保存

- 输入即时更新预览与完整度
- 800ms 防抖；只提交变化字段
- 同一时间串行保存；请求期间的新修改排队
- 状态：`等待保存 / 保存中 / 已保存 HH:mm / 保存失败`
- 离开页面前若有未保存修改，使用路由 blocker 弹窗：
  - 直接离开
  - 保存并离开
  - 右上角 X 关闭（取消跳转）
- 浏览器刷新/关闭使用 `beforeunload` 兜底

## 5. 上传与识别

上传页分两类：

1. `intro` 企业介绍文档：PDF / DOCX / PNG / JPG，单文件 ≤10MB，识别后填充企业资料
2. `identity` 企业身份验证：PDF / PNG / JPG，单文件 ≤10MB，提交审核，不做字段识别

当前前端已经实现：

- 拖拽/点选、单文件校验、文件卡片、取消识别
- `uploading → recognizing → success` 状态机与进度条
- 字段级识别结果预览：当前值、识别值、置信度、填充/覆盖状态
- 默认只勾选当前为空的字段；已有内容必须手动勾选才会覆盖
- 应用时只 `PATCH` 勾选字段，成功后返回企业资料页并提示
- 默认通过 HTTP provider 提交到后端；`VITE_RECOGNITION_PROVIDER=mock` 可切换回本地模拟
- 身份材料提交后从 `/employer/company/verification` 读取待审核/已通过/已驳回状态
- 企业资料页身份认证卡展示当前审核状态、驳回原因和重新提交入口

Provider 接口（`frontend/src/api/recognition.ts`）：

```ts
interface RecognitionProvider {
  recognize(file: File, options?: {
    signal?: AbortSignal
    onStage?: (stage: 'uploading' | 'recognizing', progress: number) => void
  }): Promise<RecognitionResult>
}
```

- `http`（默认）：上传文件、轮询后端识别任务、映射 recognition.v1 结果
- `mock`：仅用于离线联调，返回固定示例字段
- 身份提交同样支持 http/mock 两种实现

### 后端 B1：真实本地识别

介绍文档：

```http
POST /api/employer/company/documents   # multipart file，返回 202 processing
GET  /api/employer/company/documents/{id}
GET  /api/employer/company/documents/{id}/file
```

- 文件保存到 `backend/uploads/documents/{company_id}/`，数据库只存 UUID 相对路径
- PDF：优先使用文本层；文本过少的页面用 PyMuPDF 渲染后做 OCR
- DOCX：读取段落与表格文本
- PNG/JPG：使用 RapidOCR 做本地 OCR
- OCR 和规则抽取在 `BackgroundTasks` 中执行，状态 `processing → parsed/failed`
- 文件下载必须通过企业归属校验
- 依赖：`pymupdf`、`python-docx`、`Pillow`、`rapidocr`
- 课程版使用 `BackgroundTasks`，进程重启可能丢失正在识别的任务；生产环境应换独立 worker
- 识别失败会保存 `failed` 和错误原因，不返回伪造字段

### recognition.v1 payload

```json
{
  "schema_version": "recognition.v1",
  "provider": "local",
  "model": "rapidocr-onnxruntime+rule-v1",
  "document_type": "intro",
  "confidence": 0.985,
  "fields": {
    "name": {
      "value": "星河科技有限公司",
      "confidence": 0.985,
      "source": {
        "page": 1,
        "bbox": [72, 64, 320, 86],
        "text": "企业名称：星河科技有限公司",
        "method": "pdf_text"
      }
    }
  },
  "warnings": [],
  "meta": {
    "pages": 1,
    "ocr_used": false,
    "text_length": 94,
    "duration_ms": 9
  }
}
```

- `source` 记录页码/位置/原文片段/来源方法
- `meta` 记录页数、是否使用 OCR、文本长度、耗时
- 原始全文不直接返回前端，只保留字段级来源片段
- `fields` 只包含实际识别到的字段；缺失字段会写入 warnings

### 置信度

```text
字段置信度 =
  0.50 × 文本质量
+ 0.30 × 抽取方式置信度
+ 0.20 × 业务校验分
```

- 文本质量：PDF/DOCX 文本层为 1.0；OCR 使用 RapidOCR 行级 score
- 抽取方式：显式标签 0.95、下一行取值 0.90、公司后缀匹配 0.70、关键词/段落兜底 0.55–0.62
- 业务校验：电话格式、企业名称后缀、地址标记、简介长度
- 整体置信度：按名称 30%、行业 15%、电话 20%、地址 15%、简介 20% 加权；缺失字段按 0 计
- 低置信度、缺失字段、OCR 质量偏低会写入 warnings，不静默成功

### B2/B3/B4

身份认证：

```http
POST /api/employer/company/verification  # multipart file，返回 201 pending
GET  /api/employer/company/verification  # current + history
```

- 创建 `identity` 文档和 `pending` 认证申请，版本号递增
- 同一企业同时只允许一个 `pending`
- 已认证企业可以发起复审，`verified` 在审核前保持不变
- 认证材料不参与识别，也不参与资料完整度
- 提交时写入 `company_verification_events` 的 `提交申请 → pending` 事件

管理员审核：

```http
GET  /api/admin/verifications?status=pending&page=1&page_size=20
GET  /api/admin/verifications/{id}
GET  /api/admin/verifications/{id}/file
POST /api/admin/verifications/{id}/approve
POST /api/admin/verifications/{id}/reject
POST /api/admin/verifications/{id}/revoke
```

状态机：

```text
pending --通过--> approved   verified=true
pending --驳回（必填原因）--> rejected   verified=false
approved --撤销（必填原因）--> revoked    verified=false
```

- 只有 `pending` 能通过/驳回，只有 `approved` 能撤销
- 条件更新 `WHERE status=...`，并发审核只有一个管理员成功
- 审核申请、企业 `verified` 更新、事件写入在同一事务
- 审核列表支持状态筛选、分页、状态计数
- 管理端页面：`/admin/verifications`，顶栏「认证审核」
- 详情展示企业摘要、材料下载、历史版本、审核时间线
- 驳回/撤销原因至少 2 个字
- 事件记录提交、通过、驳回、撤销的操作人与备注
- 管理员之外的角色访问 403

> B4 已完成企业端真实身份提交、认证状态展示和驳回原因展示；管理端审核页属于 B3。
