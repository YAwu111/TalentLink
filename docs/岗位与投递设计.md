# 真实岗位与投递设计

## 1. 岗位状态

```text
draft ──发布──> published ──关闭──> closed
  ^                                  │
  └──────────重新发布────────────────┘
```

- 新建岗位默认 `draft`
- 发布前校验岗位名称、岗位要求、薪资和企业资料完整度
- 只有 `published` 岗位出现在求职者岗位列表
- 关闭后从列表下架，已投递记录保留

## 2. 接口

### 求职者

```http
GET  /api/jobs
GET  /api/jobs/{job_id}

POST /api/seeker/applications
GET  /api/seeker/applications
```

岗位筛选参数：

- `keyword`：岗位名称/要求/企业名称
- `city`：企业地址包含
- `industry`：企业行业
- `salary_min` / `salary_max`

### 企业

```http
GET   /api/employer/jobs
POST  /api/employer/jobs
PATCH /api/employer/jobs/{job_id}

POST  /api/employer/jobs/{job_id}/publish
POST  /api/employer/jobs/{job_id}/close

GET   /api/employer/applications?job_id=&status=
GET   /api/employer/applications/{application_id}
PATCH /api/employer/applications/{application_id}/status
```

投递状态更新请求：

```json
{ "status": "viewed" }
```

允许的目标状态：`viewed`、`interview`、`rejected`。

## 3. 投递规则

求职者点击投递时：

1. 求职者必须存在
2. 13 项资料必须完整
3. 岗位必须已发布
4. 企业资料必须完整
5. 同一 `(job_id, seeker_id)` 只能有一条投递

数据库唯一约束 `uq_applications_job_seeker` 与后端校验共同防重复。

投递成功状态为 `submitted`，状态流转：

```text
submitted ──> viewed ──> interview ──> rejected
    │            │            │
    └────────────┴────────────┴──────> rejected
```

- `submitted / viewed / interview` 可标记为 `rejected`
- `submitted / viewed` 可进入 `interview`
- `submitted` 可标记为 `viewed`
- `offered` 与 `rejected` 为终态，本轮企业接口不能把状态改为 `offered`
- Offer 发布与接受下一阶段实现

企业只能访问本企业岗位下的投递；跨企业访问返回 404。

## 4. 前端

- 求职者：岗位列表、详情、投递确认、我的投递
- 企业：岗位管理、创建/编辑弹窗、发布、关闭/重新发布
- 企业：投递管理、按岗位/状态筛选、查看求职者完整简历、打印简历
- 企业：标记已查看、安排面试、标记不合适；修改后求职者刷新可见
- 岗位与投递都来自后端，刷新不会丢失
- 岗位列表 `applied` 来自当前求职者的投递记录
- 企业岗位发布失败时展示后端错误（如企业资料不完整）
